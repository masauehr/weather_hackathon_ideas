# ID-15 自転車/徒歩ナビの「濡れない経路」— 最小スパイク（2026-09-29）

**[← experiments 一覧](../README.md)** ・ アイデア: [idea_catalog ID-15](../../docs/idea_catalog.md)

「気象庁の高解像度降水ナウキャストで、経路上の各点が『何分後に通るときに濡れるか』を判定し、
出発を遅らせれば濡れずに着けるか」を、実データで確かめた記録。

## 結論（先に）
| 問い | 結果 |
|---|---|
| 高解像度降水ナウキャスト（60分先まで）を無認証で取得できるか | **できた**。`jmatile/data/nowc/targetTimes_N2.json` で5分毎12コマの基準時刻・予測時刻一覧、タイルPNGも認証不要 |
| タイル画像から「その地点は雨か」を判定できるか | **できた**。タイルは256x256・4bitパレットPNGで、パレットindexごとに透明度(tRNS)が付いている。**実測で確認**: 「降水なし」の色（index0/1）はα=0、降水を示す色（index2以降=水色〜黄色等）はα=255。**αチャンネルだけで降雨の有無を機械的に判定できる**（正確なmm/h値は不要） |
| 出発時刻をずらす提案ができるか | **できた（ロジック検証済み）**。実データ（2026-09-29、東京は広範囲に雨で終日効果なしと判定）に加え、雨雲が15分で通過する架空データでも検証し、**「15分後に出発すれば経路上の降雨が0/10点になる」を正しく特定** |
| GO/NO-GO | **一部GO**。データ取得・判定ロジックは機械的に動く。ただし経路そのものは直線補間のMVP（下記「限界」） |

## 構成
| ファイル | 役割 |
|---|---|
| [fetch_nowcast.py](fetch_nowcast.py) | 高解像度降水ナウキャストの基準時刻・予測時刻一覧取得、タイルPNGの取得・αチャンネルでの降雨判定 |
| [route.py](route.py) | 2点間を直線補間した経路について、出発時刻を5分ずつ遅らせた候補ごとに「経路上の何点が濡れるか」を評価し最良の出発時刻を推す |
| [server.py](server.py) + [webapp/](webapp/) | ブラウザで地図上に経路・降雨タイル・推薦テーブルを表示するデモ（下記） |

実行（CLI）: `python route.py walk`（徒歩4.8km/h） / `python route.py bike`（自転車15km/h）

## Webアプリ（デモ）
```bash
python server.py       # http://127.0.0.1:8793/
```
地図（Leaflet + OpenStreetMap）に気象庁の降雨タイルを重ねて表示。クリックで出発地→到着地を指定し「評価」を押すと、
出発時刻の候補ごとの推薦テーブルと、選んだ候補の経路上の各点（☔濡れる/☀晴れ）が地図に表示される。
スライダーで実況〜60分先までのナウキャストフレームを切り替え可能。

**GitHub Pagesのような常時公開はしない**（できない）。理由:
1. 降水ナウキャストは「今から60分先まで」しか意味を持たないデータで、静的サイトに事前計算した結果を置いても数分で無意味になる。
2. 対象JSON（`targetTimes_N2.json`等）にCORSヘッダーが無く、ブラウザから直接fetchできない。`server.py`が気象庁への取得を代行する必要があり、これは動的サーバーでしか実現できない。
そのため使うときにローカルで `python server.py` を起動する運用とする。

## 仕組み
1. `targetTimes_N2.json` で直近の予測基準時刻と、60分先までの5分毎 validtime を取得
2. 経路（2点間）を等間隔の点に補間し、各点までの累積距離を計算
3. 出発時刻の候補（0, 5, 10, ... 分後）ごとに、各点への到達予定時刻を歩行/自転車速度から算出
4. 到達予定時刻に最も近い validtime のタイル（緯度経度→Web Mercatorタイル座標→ピクセル）を読み、αチャンネルで「そのときその場所が雨か」を判定
5. 濡れる点が最も少ない出発時刻を推薦

## 発見・注意
- **タイルはパレット形式（最大16色）で、各パレットindexにtRNSで透明度が入っている**。実測（2026-09-29、東京駅付近）では index0,1（白・透明）がα=0、index2〜6（薄い水色→水色→青→濃い青→黄色、降水強度が強いほど濃い色）がα=255。これにより厳密なmm/h値を知らなくても「降水の有無」は確実に判定できる。強度の相対比較（薄い水色<水色<...<黄色<橙<赤<紫、のはず）は今回は水色〜黄色までしか実データで確認できておらず、赤・紫側は未確認。
- ズームレベルはjma系実装のnativeMax（10）を採用。hrpnsの解像度（250m格子）に対して概ね妥当と考えられるが、厳密な検証はしていない。
- 実行した時点（2026-09-29 11時台JST）は東京都心が広範囲に雨で、経路上どこにいても・いつ出発しても100%濡れる結果に。出発時刻をずらす効果は**架空データ（雨雲が15分で通過するパターン）で別途ロジックのみ検証**し、正しく最良時刻を選べることを確認した。

## 限界（過大評価しないために）
1. **経路は2点間の直線補間**。実際の道路・歩道ネットワークではない。ルーティングAPI（OSRM等）と組み合わせる必要がある。
2. **降雨の強度（弱い/激しい）を区別していない**。二値判定（濡れるか否か）のみ。強度別の重み付けは未実装（パレット色の相対順位を使えば拡張可能）。
3. **実データでの「出発をずらす効果」は今回未確認**（試行時が広域降雨だったため）。架空データでのロジック検証のみ。
4. タイル座標のピクセルサンプリングは1点のみ（周辺ピクセルの平均化などはしていない）。タイル境界・ズームの丸め誤差の影響は未評価。
5. 60分先までしか予測がない（`hrpns`の高解像度ナウキャストの範囲）。長距離・長時間の経路には対応しない。

## 次にやるなら
1. 実際に降雨がまばらな日に再実行し、実データで「出発をずらすと濡れずに着ける」ケースを確認する。
2. パレット色の強度順位（水色系→黄色→橙→赤→紫）を使い、二値でなく強度スコアで経路を比較する。
3. 徒歩・自転車のルーティング（OSRM等の公開/無料API）と組み合わせ、直線でなく実際の道路経路で評価する。
4. 「あと5分待てば止む」のような自然言語の提案文をLLMで生成する（GenAI要素、idea_catalogの★案）。
