# ID-32 天気図VLM解説 — 最小スパイク（2026-09-25）

**[← experiments 一覧](../README.md)** ・ 設計: [c32_weather_chart_vlm.md](../../docs/candidates/c32_weather_chart_vlm.md)

「天気図＋衛星を VLM に読ませ、実況・予報でガードレールをかけられるか」を、1事例で通しで確かめた記録。
データはすべて気象庁（公開）。個人データは不使用。出典: 気象庁ホームページ。

## VLM とは
**VLM（Vision-Language Model、視覚言語モデル）** は、画像とテキストの両方を入力に受け取り、テキストで答えるAIモデル。

| | 入力 | 出力 |
|---|---|---|
| LLM | テキストのみ | テキスト |
| VLM | 画像 ＋ テキスト | テキスト |

- 写真・グラフ・スクリーンショット・天気図などを見て「何が写っているか」「何が読み取れるか」を言葉で答える。Claude は画像対応のため VLM として使える。
- **本アイデア（ID-32）での役割**: 天気図・衛星画像とアメダス実況（テキスト）を一緒に渡し、①高気圧・低気圧・前線・台風の位置と気圧配置の型の判定、②「なぜこの天気か・明日どうなるか」の平文解説、を出させる。天気図は等圧線・前線記号・示度が密に描かれた画像で、従来は専用の画像処理が必要だった。VLM なら画像を渡すだけで読める点が「生成AIの必然性」。
- **注意**: 画像の細部（示度の数字、前線の位置など）を**もっともらしく読み違える**ことがある。そのため本スパイクでは、ラベルの許可リスト・季節整合・数値引用チェック・実況突合・予報突合のガードレールで出力を検証している（→ [validate.py](validate.py)）。
- 本スパイクでは API キー未設定のため、Claude Code セッション自身を VLM 役として使った（詳細は「限界」参照）。

## 結論（先に）
| 問い | 結果 |
|---|---|
| 気象庁の天気図・衛星を自動で取れるか | **できた。** 認証なし・bosai の JSON/PNG/タイルのみ。ファイル名から対象時刻も取れ、衛星・アメダスを天気図に時刻合わせできる |
| VLM 相当が天気図から気圧配置を読めるか | **1事例では読めた。** 高気圧・低気圧・停滞前線・台風の位置と移動方向、示度（1020/1016/1012/1014/1000hPa）を読み取り、府県予報の概況（高気圧に緩やかに覆われる／前線が西から／北海道に気圧の谷）と矛盾なし |
| ガードレールは機能するか | **機能した（合成テスト 3/3）。** ただし最初は 2/3 で、「許可リスト内の季節外れラベル（9月に冬型）」を見逃した → 季節整合ルールを追加して解消 |
| GO/NO-GO | **一部GO。** 取得〜検証の配管は成立。VLM の**精度**（多数事例）はまだ未検証 |

## 取得元（入手性 / ライセンス / 粒度 / 遅延）
| データ | URL 系統（`https://www.jma.go.jp/bosai/`） | 粒度・遅延 |
|---|---|---|
| 地上天気図 | `weather_map/data/list.json` → `weather_map/data/png/<ファイル名>` | 日本近海 3時間毎(実測は約2時間遅れで掲載)、アジア 6時間毎。PNG 約600px |
| ひまわり赤外 | `himawari/data/satimg/targetTimes_fd.json` → `.../{base}/fd/{valid}/B13/TBB/{z}/{x}/{y}.jpg` | 10分毎、遅延は数分。`jp` 域は斜めに欠けた範囲で太平洋側が空白になるため `fd` の z=4 タイルを使う |
| アメダス | `amedas/data/map/{YYYYMMDDHHMMSS(JST)}.json` | 10分毎。値は [値, 品質] 形式 |
| 府県予報概況 | `forecast/data/overview_forecast/{office}.json` | 日3回程度 |
入手性は認証不要。ライセンスは気象庁HP利用規約に従う（出典明記）。

## 発見・注意
- **実況の時刻ずれ**: 最初は最新アメダス（15時JST）と天気図（12時JST）を混ぜていた。時刻合わせが必須で、`fetch_chart.py` は天気図の対象時刻を基準に統一済み。
- **許可リストだけでは足りない**: ラベルの形式チェックと「中身の妥当性」は別。季節整合のような外部知識ルールが要る。
- 設計書の「数値は実況JSONから引用」は、**天気図上の示度（hPa）には適用できない**（アメダスに無い値）。示度は `chart_values` に分離し、要目視確認 or 別途 OCR/突合が必要。

## 限界（過大評価しないために）
1. **事例1件・1日のみ**。「秋の穏やかな日」で難易度は低い。冬型・南岸低気圧・台風接近など難しい型は未検証。
2. **VLM 役は Claude Code セッション**（API キー未設定）。外部 API 経由の再現性・遅延・コストは未測定。
3. **完全な盲検ではない**。画像を見る前に府県予報の概況とアメダスを読んでいたため、特に `tomorrow` の予報一致は割り引いて見ること（`today` の気圧配置の読みは画像由来だが、これも汚染ゼロとは言えない）。
4. `validate.py` の数値引用チェックは文字列の部分一致で甘い（短い数字は誤って通りうる）。突合の合成テストも自作で、実 VLM の誤りの型を網羅していない。
5. 赤外画像の雲の解釈（帯状雲＝前線等）は目視のみで、定量評価していない。
